## 五、客户端 img 处理 + 踩坑（重要，要和 20260929 那份文档一起看）

做法：用 OrzRepacker MCP（`copy_nodes` 从 059 的 img 复制整棵节点树 → `paste_nodes` 粘到目标 img → `save_node`），
比一个节点一个节点建快，也能保住 canvas 数据。

头字段 offset 0x0C 的真实含义是"根节点数量"，不是"数据偏移"（这次实测确认）：

- 数量小于实际 → 新加的节点读不出来（客户端里地图名/任务名看不到）；
- 数量大于实际 → 文件直接读崩（MCP 的 `list_children` 返回 -1）。
- OrzRepacker 保存时写的是"加载时"的旧数量，所以「粘贴节点 → 保存」以后新节点是隐藏的，必须把数量改对：

| 文件 | 原字段 | 改成 | 规则 |
|---|---|---|---|
| `Quest\QuestInfo.img` | 0x00033C80 | 0x00034F80 | 低字节 0x80 的文件：+0x100 x 新增根节点数（+19） |
| `Quest\Check.img` | 0x00033A80 | 0x00034D80 | 同上 |
| `Quest\Act.img` | 0x00033B80 | 0x00034E80 | 同上 |
| `Quest\Say.img` | 0x00033C80 | 0x00034F80 | 同上 |
| `String\Map.img` | 0xC7FB0009 | 0xC7FB000A | 低 16 位就是数量：+1 |
| `String\Npc.img` | 0x001BD380 | 0x001BD480 | 低字节 0x80 规则：+0x100（+1 个 9310059） |
| `String\Mob.img` | 0x00034080 | 0x00034280 | 同上（+2 个） |
| `Map\MapHelper.img` | 0xDDF90005 | 不动 | 新增的 `mark/Thai` 是嵌套节点，根数量仍是 5；动了读崩 |

改法：`open(path,'r+b')` + `seek(12)` + 写 4 字节（MCP 加载过文件后 `open(...,'wb')` 会 EINVAL/被占用，
但 `r+b` 原地写可以；也可以让工具 `save_as` 写到临时文件，再把整块内容读出来用 `r+b` 覆盖）。

20260929 文档 §8 的结论需要修正：那次把 Quest img 的字段"改回旧值"只是让客户端不崩，
副作用是新加的 8515/8516-8527 等节点在客户端里读不出来（这次确认 8516-8527 在客户端 QuestInfo.img 里确实没有）。

验证方法（不用开客户端）：MCP `load_files` → `find_node` 能看到节点 = 数量对了；
`list_children` 返回 -1 = 数量改大了。
