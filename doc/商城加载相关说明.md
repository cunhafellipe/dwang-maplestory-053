# 商城加载相关说明（客户端 + 服务端）

> 原名「商城道具上架说明」；2026-10-15 改名并补充**商城显示顺序**（§0.2 排序规则 / §6.6 按地区重排实例）。

> 适用：GMS053 版（`E:\game\ms\gms053`，客户端 = `v53-client`，服务端 = `gms53-Server`）
> 目的：把一件（或一批）道具放进商城卖，需要改哪些文件、按什么规则分配 SN、怎么验证。
> 本文以「昭和 / 豫园 15 张美容会员卡上架」为例，规则对任何商城道具都通用。

---

## 0. 先搞清楚数据流（最重要）

商城的**展示**和**购买**是两套数据，分别归客户端和服务端管：

| 环节 | 谁的数据 | 说明 |
|---|---|---|
| 商城顶部标签（上衣/裤裙/美容美发…） | **客户端** `Data/Etc/Category.img` | 标签名取该节点的 `Name`，该标签里显示哪些商品由同一条节点的 `Category`+`CategorySub` 决定（拼成 SN 前缀） |
| 商城商品列表（有哪些、多少钱、图标） | **客户端** `Data/Etc/Commodity.img` + `Data/String/Item.img` + `Data/Item/Cash/*.img` | 进商城时服务端只发 `openCashShop / 现金背包 / 礼物 / 心愿单 / 点券`，**不发商品表**；列表完全是客户端本地数据 |
| 购买（扣点券、发货、进现金背包） | **服务端** `wz-zh-CN/Etc.wz/Commodity.img.xml` | 客户端买的时候只发一个 **SN**，服务端按 SN 查自己的商品表（再用 `modified_cash_item` 表覆盖价格/期限等） |
| 管理后台"商城管理"页 | **服务端** WZ + `modified_cash_item` 表 | `/cashShop/v1/*`（分类、按分类查商品、单个/批量上架） |

**结论：同一个 SN 必须同时存在于客户端和服务端两边。**

* 只加服务端 → 商城界面上根本看不到这件商品。
* 只加客户端 → 能看到、能点，但购买时服务端 `CashItemFactory.getItem(sn)` 返回 null，交易失败（扣不了钱/发不了货）。

### 0.1 进商城时服务端到底发了什么（`SET_CASH_SHOP 0x4F`）

`PacketCreator.openCashShop()` 依次写：

1. `nNotSaleCount`（"不卖的商品"数量和 id 列表）——**本服固定写 0**，是个可用的开关（见下）；
2. `modified_cash_item` 表里的**全部覆盖记录**（每条 = SN + 字段掩码 + 置位字段）。字段掩码/顺序是 **053 客户端** 的表，见 `org.gms.server.cashshop.CommodityFlag`（和 083 的表不同，别照抄 083 的文档）；
3. 各标签"销量最好 top 8"的 SN 列表（`World#getMostSellerCashItems`，玩家购买时 `addCashItemBought(sn)` 累计）；
4. 库存 / 限时限量（都写 0）、`writeByte(0)`、`writeInt(75)`。

也就是说：

* **服务端能「改」已存在的 SN**（价格/期限/上架状态会推给客户端覆盖显示）。封包里的 SN 如果在客户端 `Commodity.img` 里找不到，客户端 `SetSaleInfo` 会**新建一条**（`GMSv53.exe:0x77D4BE` 附近：构造 `CS_COMMODITY` → `DecodeModifiedData` → `InsertBefore`），也就是说理论上能用 `modified_cash_item` 塞一条客户端没有的 SN；但封包里没发的字段就是 0，名字/图标仍然要客户端 `String/Item.img`、`Item/Cash` 里有，而且管理后台的 `changeOnSale` 要求 WZ 里先有该 SN —— 所以**正常做法还是服务端 + 客户端两边都写**。
* 想让某件客户端列表里已有、但暂时不卖的商品消失，其实可以不用动客户端：把 `nNotSaleCount` 那段填上 SN（目前代码写死 0，需要改代码）。
* 客户端点标签**不会**向服务端要商品表：`CHECK_CASH(0xAA)` ↔ `TouchingCashShopHandler` 只回一个 `showCash`（点券数量）。所以列表 100% 来自客户端本地 `Data/Etc/Commodity.img`。

### 0.2 商品在页签里的顺序（客户端排序规则）

商品在**页签里的位置**跟 SN 无关，是客户端自己排的（053 反汇编确认）：

进商城时 `CWvsContext::LoadCommodity`（`GMSv53.exe:0x77CAAB`）先读客户端 `Data/Etc/Commodity.img` 建基础表 →
`CWvsContext::SortCommodityBySN`（`0x77CB4F`）**整表按 SN 升序** → 按 SN 前 3 位切成页签
（`cat = SN/10000000 % 10`、`sub = SN/100000 % 100`，见 `CCashShop::GetCategorySubIndex` `0x45350C`；
前缀在 `Category.img` 里找不到就抛 `CTerminateException` 掉线）→ 再由 `CCashShop::LoadData`（`0x45388E`）
对**每个页签内部**连做三段排序，**最后一段是主键**：

| 顺序 | 排序键 | 字段（`CS_COMMODITY` 偏移） | 方向 |
|---|---|---|---|
| 主键 | **`Priority`** | +0x24（Commodity.img 的 `Priority`） | **降序**（值大的排前面） |
| 次键 | `OnSale` | +0x40 | 降序（在售的排前面） |
| 末键 | `ItemId` | +0x10（`TSecType` 加密字段） | 升序（值小的排前面） |

* 一句话：**SN 决定「进哪个页签」，`Priority` 决定「在页签里排第几」。**
* 客户端**没有「按名字排序」的键**（名字只在绘制时去 `String/Item.img` 里查）。想按中文名 / 按地区 / 按任何自定义顺序排，
  就离线把顺序算好、换算成一串 `Priority` 写进 Commodity。服务端封包里 `Priority` 只发 1 字节，取值 **0~255**；
  一个页签最多 256 个不同优先级，超了就只能靠 `ItemId` 兜底。
* 同一优先级内按 `ItemId` 升序，而 `ItemId` 的千位段天然分组（`5150xxx` 发型 / `5151xxx` 染色 / `5152xxx` 整形·美瞳 / `5153xxx` 护肤），
  所以「一个地区一个优先级」顺手就能得到「发型→染色→整形→美瞳→护肤」的顺序。
* 管理后台（`CashShopApiService#getCommodityByCategory`）也是 `Priority 降序 + ItemId 升序`，和游戏里看到的一致。
* 页签里**未上架**（`OnSale=0`）的条目也仍然在列表里，只是 `OnSale` 只是次键 —— 想让它们沉到本地区最后，
  要把在售的写成「段+2」、未上架的写成「段+1」；想让它们**彻底消失**，见 §0.1 的 `nNotSaleCount`。
* 实例见 §6.6（美容美发整页按地区重排）。

## 1. SN 编码规则（决定商品出现在哪个标签）

SN 是 **8 位数字**，格式固定为 `C` + `SS` + `NNNNN`：

```
5 00 00170
│ │  └──── 同类内自增的 5 位序号（自己分配，不能和已有 SN 重复）
│ └─────── CategorySub（2 位）＝ Category.img 里的子类号
└───────── Category    （1 位）＝ 大类
```

* 商城标签 = `Category.img` 里 `(Category, CategorySub)` 对应那一条。
* 页签内部谁前谁后由 `Priority` 决定（不是 SN），规则见 §0.2。
* 想让商品出现在某个标签下，SN 前缀就用那个 `Category + %02d(CategorySub)`。
* 服务端就是这么过滤的：

```java
// CashItemFactory#getCommodityByCategory
final String prefix = data.getId() + String.format("%02d", data.getSubId());
filter(cashItem -> String.valueOf(cashItem.getSn()).startsWith(prefix))
```

常用前缀对照（`wz-zh-CN/Etc.wz/Category.img.xml`）：

| 前缀 | Category/Sub | 标签 |
|---|---|---|
| 100 | 1/0 | 新品 |
| 101 | 1/1 | 活动 |
| 200 | 2/0 | 帽子 |
| 201 / 202 / 203 | 2/1 · 2/2 · 2/3 | 脸饰 / 眼饰 / 长袍 |
| **204 / 205 / 206** | 2/4 · 2/5 · 2/6 | **上衣 / 裤裙 / 鞋子** |
| 207 / 208 / 209 / 211 | 2/7 · 2/8 · 2/9 · 2/11 | 手套 / 武器 / 戒指 / 披风 |
| 300 / 301 / 302 | 3/0 · 3/1 · 3/2 | 卷轴 / 通讯物品 / 天气 |
| **500** | **5/0** | **美容美发** ← 美容卡放这里 |
| 501 / 502 / 505 | 5/1 · 5/2 · 5/5 | 个人商店 / 游戏 / 效果 |
| 600 / 601 / 602 | 6/0 · 6/1 · 6/2 | 宠物 / 宠物装备 / 宠物消耗 |
| 700 | 7/0 | 礼包 |

> 例：`50000170` = 5/00/00170 → 出现在「美容美发」标签。
> 分配新 SN 前，先在 `Commodity.img.xml` 里搜一下 `5000017` 之类确认没被占用。

## 2. 一条 Commodity 记录长什么样

服务端 XML（`gms-server/gms-handler/wz-zh-CN/Etc.wz/Commodity.img.xml`）：

```xml
    <imgdir name="4482">                     <!-- 节点名＝文件内序号，随便起，别重复 -->
        <int name="SN" value="50000039"/>    <!-- 8 位 SN，商品唯一标识 -->
        <int name="ItemId" value="5150001"/> <!-- 卖的道具 id -->
        <int name="Count" value="1"/>        <!-- 一次买给几个 -->
        <int name="Price" value="5700"/>     <!-- 点券价 -->
        <int name="Period" value="-1"/>      <!-- 有效期(天)，-1 = 不限时；宠物服务端强制 90 -->
        <int name="Priority" value="9"/>     <!-- 客户端排序用，大的排前面 -->
        <int name="reqLev" value="0"/>       <!-- 需求等级 -->
        <int name="Gender" value="2"/>       <!-- 2=不限，0=男，1=女 -->
        <int name="OnSale" value="1"/>       <!-- 1=上架显示，0=隐藏 -->
        <int name="Class" value="2"/>        <!-- 可选：053 客户端会读的一个标记位(0x400)，库里 0/2/3 都有，普通商品不写 -->
    </imgdir>
```

字段要点：

* `OnSale` 是**是否显示**的开关。同一件道具允许配多条 SN：一条 `OnSale=1`（商城显示的），若干条 `OnSale=0`（不同来源/不同价，隐藏）。全库 5192 条里 1515 条是 `OnSale=1`。
* `Period`：053 的数据里美容卡统一用 `-1`（不限时）。服务端 `CashItemFactory` 只对宠物强制 90 天。
* `Priority`：客户端列表顺序（`1` 字节，见 `CommodityFlag.PRIORITY`）。
* `Class`：可选标记位，库里出现 0/2/3；不写也能正常卖。
* 可选字段（本服数据里大部分没写）：`Class`、`PbCash`、`PbPoint`、`PbGift`、`Bonus`、`MaplePoint`、`Meso`、`ForPremiumUser`、`PackageSN`（礼包内容在 `CashPackage.img`，`PackageSN` 字段全库 0 条）。
* 打包给客户端的字段掩码/顺序见 `org.gms.server.cashshop.CommodityFlag`（**053 专用**，跟 083 不一样）。

## 3. 上架一件商品需要动的东西（清单）

| # | 层 | 文件 / 表 | 作用 | 是否必须 |
|---|---|---|---|---|
| 1 | 服务端 | `gms-server/gms-handler/wz-zh-CN/Etc.wz/Commodity.img.xml` | 服务端商品表（购买时按 SN 查） | **必须** |
| 2 | 客户端 | `client-dist/data/Data/Etc/Commodity.img`（→ 客户端 `Data/Etc/Commodity.img`） | 商城列表数据 | **必须** |
| 3 | 服务端 | `gms-server/gms-handler/wz-zh-CN/String.wz/Cash.img.xml` | 名称/说明（`ItemInformationProvider.getNameDesc` 读 `String.wz/Cash.img`） | **必须**（否则名字为 null） |
| 4 | 客户端 | `client-dist/data/Data/String/Item.img` → `Cash/<itemId>` | 名称/说明 | **必须**（否则显示 NO-NAME/空白） |
| 5 | 服务端 | `gms-server/gms-handler/wz/Item.wz/Cash/05xx.img.xml` | 道具规格（服务端只用到 `info/cash` 等，不需要图标） | 一般已有；缺了要补 |
| 6 | 客户端 | `client-dist/data/Data/Item/Cash/05xx.img` → `05xxxxx` | **图标** | **必须**（缺了是空白方块） |
| 7 | 服务端 DB | `modified_cash_item` 表 | 覆盖价格/数量/期限/上下架状态（管理后台写这张表） | 可选 |
| 8 | 客户端 | `client-dist/data/Data/Etc/Category.img` | 标签名 | 只有新增标签才要改（见第 6 节坑） |
| 9 | 客户端 | `client-dist/data/Data/Etc/CashPackage.img` | 礼包内容 | 只有礼包要改 |

道具 id → 文件名的对应：`5150014` → `Item/Cash/0515.img` 里的节点 `05150014`（**客户端节点名带前导 0，共 8 位**；服务端 XML 里的 `imgdir name` 也是 8 位补零形式，例如 `05150014`）。
文件名规则：道具 id 先左补 0 成 8 位当**节点名**（`5150014` → `05150014`），**文件名 = 节点名前 4 位**（也就是 `道具id ÷ 10000` 左补 0 到 4 位）：
`5150014` → `Item/Cash/0515.img`、`5010000` → `0501.img`、`5210000` → `0521.img`。

## 4. 完整操作步骤（复制粘贴级）

### 步骤 1：定 SN
1. 决定放哪个标签 → 得到 3 位前缀（美容卡 = `500`）。
2. 在 `Commodity.img.xml` 搜 `value="500` 看已用到哪：当前 `500` 段已用到 `50000177`（`50000025`~`50000031` 是豫园卡、`50000170`~`50000177` 是昭和卡），**下一个空号是 `50000178`**。
3. 一件商品一个 SN，不要复用。

### 步骤 2：服务端加 Commodity 记录
打开 `gms-server/gms-handler/wz-zh-CN/Etc.wz/Commodity.img.xml`，在**最后一个 `</imgdir>` 之前**插入新节点（节点名用当前最大序号 +1，当前文件最大是 `5191`）：

```xml
    <imgdir name="5192">
        <int name="SN" value="50000170"/>
        ...
    </imgdir>
```

> 也可以用 OrzRepacker / MCP 直接改，但注意：**服务端读的是 XML，客户端读的是 .img，两边要分别改。**

### 步骤 3：客户端加 Commodity 记录（关键，别漏）
用 OrzRepacker（见第 5 节）打开 `client-dist\data\Data\Etc\Commodity.img`（key＝**新版本客户端**），在根节点末尾新建一个节点：

* 节点名：当前最大序号 +1（053 客户端该文件是 `0`~`5191`，所以从 `5192` 开始，与 XML 保持一致最好）
* 子属性（依次）：`SN`(int)、`ItemId`(int)、`Count`(int)、`Price`(int)、`Period`(int)、`Priority`(int)、`reqLev`(int)、`Gender`(int)、`OnSale`(int)

保存 → 关闭 OrzRepacker（它占文件）→ 跑 `client-dist\tools\make-manifest.ps1` 重算清单。

### 步骤 4/5：名称与说明
* 服务端：`gms-server/gms-handler/wz-zh-CN/String.wz/Cash.img.xml`
  ```xml
      <imgdir name="5150014">
          <string name="name" value="豫园美发店一般会员卡"/>
          <string name="desc" value="在豫园美发店可以用一般的会员卡。发型随机。"/>
      </imgdir>
  ```
* 客户端：`client-dist\data\Data\String\Item.img` → `Cash` → `5150014`（`name` / `desc` 两个 string）
* 注意服务端 English 的 `wz/String.wz/` **没有** `Cash.img.xml`，所以中文名必须写在 `wz-zh-CN/String.wz/Cash.img.xml` 里（语言目录优先）。

### 步骤 6：道具规格与图标
* 服务端：`wz/Item.wz/Cash/0515.img.xml` 里加节点 `0515xxxx`，内容至少：
  ```xml
      <imgdir name="05150014">
          <imgdir name="info">
              <canvas name="icon" width="32" height="27"><vector name="origin" x="0" y="27"/></canvas>
              <canvas name="iconRaw" width="32" height="23"><vector name="origin" x="0" y="27"/></canvas>
              <int name="cash" value="1"/>
          </imgdir>
      </imgdir>
  ```
  （服务端 XML 里 canvas 没有 png 数据，只有宽高/origin，够用。）
* 客户端：`Data/Item/Cash/0515.img` 里必须有对应节点 **并且带图标（icon / iconRaw 的 png）**，否则商城是空白方块。

### 步骤 7：生效
* **服务端**：每次启动时 `CashItemFactory.loadAllCashItems()` 读 Commodity/CashPackage/Category；改了 WZ 要**重启服务端**。只改 `modified_cash_item` 表则会自动重载（`loadAllModifiedCashItems()`）。
* **客户端**：把改好的文件同步到客户端目录：
  ```
  client-dist\tools\更新客户端.bat          （= sync-client.ps1，按 client-dist.sha256 增量同步）
  ```
  然后重开商城即可（不用重启客户端）。

### 步骤 8：验证
* 游戏内：进商城 → 对应标签 → 看到商品、图标、价格。
* 管理后台：`POST /cashShop/v1/getCommodityByCategory`（body `{"data":{"id":5,"subId":0}}`）应能查到新 SN；`POST /cashShop/v1/onSale` 可改价/上下架。
* 想批量改价：`/cashShop/v1/batchOnSale`（`type` 取 `价格`/`数量`/`有效期`）。
* 注意：`modified_cash_item` 只是覆盖表，**SN 必须先存在于 WZ**，否则后台也上不了架（`CashItemFactory.changeOnSale` 会 NPE）。

## 5. 工具：OrzRepacker（GUI）与 MCP

* 工具目录：`E:\game\ms\tool\orange-wz`，双击 `OrzRepacker.bat` 启动（日志在 `logs\yyyy-MM\`）。
* 打开不同来源的 .img 要选对 key（工具里的"密钥"）：

| 数据 | key | IV |
|---|---|---|
| 053 客户端 `v53-client\Data\*.img`、`client-dist\data\Data\*.img` | 新版本客户端 | 全 0（keystream 全 0，等于明文） |
| 083 客户端 `BeiDou-Client\Data\*.img` | GMS | `4D 23 C7 2B` |

  （MCP 调用时需要显式给 base64：053 → `ivBase64="AAAAAA=="`，`GMS` → `ivBase64="TSPHKw=="` + 128 字节 DefaultKey。）
* 该工具同时是 MCP 服务（默认 `http://127.0.0.1:10002/mcp`），可用 `load_files / get_node_tree_json / mutate_nodes(set_value) / save_node` 直接改值。
* **保存有风险**：保存会重写整个 .img，先备份原文件；保存后核对文件大小与其它节点没被改坏。
* `02`/`03` 开头以外的 `.bak`、`.orzrepacker-raw` 是工具中间产物，别误当数据提交。

## 7. 常见坑

1. **只加一边**：只加服务端 = 看不见；只加客户端 = 能看见但买不了。
2. **忘了 `OnSale=1`**：加了记录也不显示。
3. **SN 撞车**：同 SN 会被已存在的那条覆盖（客户端列表按 SN 找商品）。
4. **SN 前缀选错**：商品会跑到别的标签下（或被"热度/新品"标签吸走）。
5. **客户端节点名没补零**：`05150014` 写成 `5150014` 客户端找不到图标。
6. **服务端没重启**：Commodity 是启动期加载的（`CashItemFactory.loadAllCashItems()`）。
7. **管理后台改价无效**：`modified_cash_item` 只能覆盖已存在的 SN；SN 不存在时后台也上不了架。
8. **改了 `Category.img` 导致全商城标签串位**：`Name` 必须和同一条节点的 `Category`/`CategorySub` 对齐 —— 客户端是"用这条节点的 Name 当标签文字，用这条节点的 Category+CategorySub 去筛 SN"。历史上就踩过一次，见第 8 节。

## 8. 附：客户端商城"标签与商品错位"的根因（2026-10 已定位并修）

**现象**：点「上衣」出来「裤裙」的东西，点「裤裙」出来「鞋子」的东西（整块往后串了一位）。

**根因**：客户端 `Data/Etc/Category.img` 是在 2026-09-21 用 OrzRepacker 从
`E:\game\ms\gms053\汉化\cn-v1-xml\Etc.wz\Category.img.xml`（一份**汉化时 Name 与 Category/CategorySub 整体错位一格**的 XML）整包导入导出的，于是客户端文件里：

```
[6] Category=2 CategorySub=4  Name=长袍   ← 应该是「上衣」
[7] Category=2 CategorySub=5  Name=上衣   ← 点它就出 sub=5（裤裙）的商品
[8] Category=2 CategorySub=6  Name=裤裙   ← 点它就出 sub=6（鞋子）的商品
```

客户端用**同一条节点**的 `Name` 当标签、用 `Category+CategorySub` 拼 SN 前缀来选择商品，所以名字错位 = 标签和内容错位。

**已修**：
* 客户端：`client-dist\data\Data\Etc\Category.img` 的 Name 已与 Category/CategorySub 对齐，并把 `(2,4)` 从「热销」改成「上衣」（原本那份虽然对齐了，但把 Top 误译成了"热销"）。
* 服务端：`gms-server/gms-handler/wz-zh-CN/Etc.wz/Category.img.xml` 同步把 `(2,4)` 的 Name 改成「上衣」。
* 客户端目录里的旧文件要跑 `client-dist\tools\更新客户端.bat` 才会被替换（`v53-client\Data\Etc\Category.img` 一直是 2026-09-21 的旧文件）。

**自查方法**：比较三个文件的 `(Category, CategorySub, Name)` 三元组是否一一对应 ——
`wz-zh-CN/Etc.wz/Category.img.xml`、`client-dist/data/Data/Etc/Category.img`、客户端 `Data/Etc/Category.img`。
正确的对应关系（子类 4 必须是「上衣」，5「裤裙」，6「鞋子」）：

```
2/0 帽子  2/1 脸饰  2/2 眼饰  2/3 长袍  2/4 上衣  2/5 裤裙  2/6 鞋子  2/7 手套  2/8 武器  2/9 戒指  2/10 勋章  2/11 披风
```

## 9. 速查：改一个已有商品的价格 / 上下架

前提：这个 SN 已经**同时**存在于客户端 `Commodity.img` 和服务端 `Commodity.img.xml`。三种做法：

1. **只在管理后台改**（`modified_cash_item`，`/cashShop/v1/onSale` 或 `batchOnSale`）
   * 服务端立刻生效（实扣价按覆盖值），并且进商城时会把覆盖记录推给客户端（见 0.1），客户端显示的价格通常会跟着变。
   * 若发现客户端仍显示旧价，就用第 2 种做法两边一起改，最稳。
2. **两边 Commodity 都改**（客户端 `Commodity.img` + 服务端 `Commodity.img.xml`）
   * 改完服务端要**重启**；客户端改完要同步（`更新客户端.bat`）并重进商城。
   * 这是唯一"绝对一致"的做法。
3. **只改一边**（不推荐）
   * 只改服务端：客户端显示旧价，实扣新价 → 价格对不上。
   * 只改客户端：客户端显示新价，实扣旧价 → 玩家会吃亏/占便宜。

上下架：把 `OnSale` 改成 `0` 两边都不显示；DB 的 `on_sale=0` 覆盖也能让客户端把它当"不卖"（`modified_cash_item.on_sale` 会随 `SET_CASH_SHOP` 推给客户端）。
